# 鲜果记企业级落地评估与优化路线图

> 本文档用于承载项目复盘后的企业级落地建议，避免污染原有 `PRODUCTION_OPTIMIZATION_PLAN.md`。
>
> 当前阶段明确边界：**支付、退款功能先预留真实通道，只实现模拟能力**。因此近期优化重点不是微信支付接入，而是状态机正确性、安全加固、部署运维、测试质量、监控告警、权限治理与工程化。

---

## 1. 当前结论

鲜果记已经具备较完整的单商户生鲜电商系统雏形，包含用户端、商家端、后端、数据库、部署脚本和测试规划。项目不是简单 Demo，已经有较多生产化意识，例如 JWT 加固、XSS 防护、SQL 注入防御、热点限流、IP 封禁、安全响应头、Docker 部署、生产 profile 等。

但如果按企业级正式生产标准，目前仍需要补齐以下能力：

- **模拟支付/退款状态机闭环**：本阶段不接真实支付，但订单状态、退款状态和幂等必须可靠。
- **上传安全深度校验**：不能只依赖后缀和 Content-Type。
- **生产配置启动前校验**：避免带着弱密钥、开放 CORS、Swagger 暴露等配置上线。
- **部署与网络隔离**：MySQL、Redis、应用端口不能暴露公网。
- **CI/CD 与质量门禁**：测试、扫描、构建、发布、回滚需要自动化。
- **监控日志告警**：线上问题要可发现、可定位、可追溯。
- **权限与越权治理**：用户资源归属、商家端角色权限需要系统化。
- **备份恢复与审计**：数据安全与操作留痕需要可验证。

## 2. 当前阶段边界

### 2.1 本阶段要做

- 模拟支付：用户点击支付后，后端完成订单状态流转、写状态日志、返回模拟支付结果。
- 模拟退款：商家审核或系统处理后，后端完成退款状态流转、写状态日志、返回模拟退款结果。
- 订单、库存、优惠券、拼团、退款的状态机和幂等保护必须真实可靠。
- 所有接口按真实生产系统标准做鉴权、限流、越权校验、日志脱敏和异常处理。

### 2.2 本阶段不做

- 不接微信支付统一下单。
- 不开放微信支付回调入口。
- 不接微信退款 API。
- 不做真实资金对账。
- 不处理微信支付证书、平台证书、回调验签、资金差错等真实支付专项。

### 2.3 未来预留

- `OrderService.pay` 后续可替换为 `WechatPayService.unifiedOrder`。
- 退款完成逻辑后续可替换为 `WechatRefundService.createRefund`。
- 预留 `pay_channel`、`transaction_id`、`refund_channel`、`refund_transaction_id` 等字段时，当前可写入 `MOCK` / `mock_xxx` 值。

## 3. P0：当前阶段必须优先完成

### 3.1 模拟支付与模拟退款状态机

**目标**

虽然不接真实支付，但订单状态必须像真实支付一样严谨，避免后续接微信支付时大改。

**建议改造点**

- `OrderServiceImpl.pay(Long uid, String orderNo)`：
  - 校验订单归属：`order.userId == uid`。
  - 仅允许 `PENDING_PAY` 进入模拟支付。
  - 使用 `Redisson` 锁：`lock:order:pay:{orderNo}`。
  - 二次查询订单，避免锁等待期间状态已变化。
  - 状态流转：`PENDING_PAY -> PENDING_ACCEPT`。
  - 写订单状态日志：备注 `模拟支付成功`。
  - 返回结构建议包含：`payNo`、`orderNo`、`payChannel: MOCK`、`paidAt`、`status`。

- 退款处理逻辑：
  - 用户申请退款只创建或复用一条有效退款单。
  - 商家审核通过后进入 `REFUNDING`。
  - 模拟退款完成后进入 `REFUNDED`。
  - 重复触发模拟退款时返回当前退款状态，不重复生成退款单。
  - 状态日志备注 `模拟退款完成`。

**验收**

- 同一订单并发点击支付 20 次，最终只产生一次有效状态流转。
- 已取消、已退款、已完成订单再次支付必须失败。
- 同一订单连续申请退款，不应出现多条有效退款流程。
- 订单状态日志能完整还原：下单、支付、申请退款、审核、退款完成。

### 3.2 文件上传安全加固

**现状风险**

当前上传入口主要按后缀判断，头像与图片上传场景对真实文件类型、EXIF、文件大小、公共入口频控仍需加强。

**建议改造**

- 用户头像、评价晒单图片限制为 `5MB`。
- 商家商品图限制为 `10MB`，如确需高清大图再单独配置。
- 后端按 magic number 校验真实文件类型，不能只信任后缀和 `Content-Type`。
- 禁止上传 `.svg`、`.html`、`.js`、`.php` 等可执行或可嵌入脚本的格式。
- 图片保存前统一生成 UUID 文件名，不使用原始文件名。
- 对图片进行重新编码或压缩，剥离 EXIF。
- 公共头像上传接口增加限流，建议同 IP 每分钟不超过 10 次。
- 生产环境优先使用 OSS + CDN，不建议直接暴露本地 `/static/**`。

**验收**

- 伪装为 `.png` 的脚本文件上传失败。
- 12MB 用户头像上传失败。
- 文件访问 URL 中不出现用户原始文件名。
- 上传接口被刷时返回 429 或被 IP 风控记录。

### 3.3 生产配置与启动前校验

**目标**

生产环境启动时主动阻断危险配置，避免弱密钥、开放 CORS、Swagger 暴露等问题进入线上。

**建议改造**

新增启动校验组件，例如 `ProductionConfigValidator`：

- `spring.profiles.active=prod` 时启用。
- 校验 `JWT_SECRET_V1` 或当前 `active-kid` 对应密钥必须存在且长度足够。
- 校验 `MYSQL_PASSWORD`、`REDIS_PASSWORD` 不为空。
- 校验 `CORS_ALLOWED_ORIGINS` 不为空且不包含 `*`。
- 校验 Swagger / Knife4j 在生产关闭。
- 校验上传大小不超过生产阈值。
- 校验 `logging.level.root` 不低于 `info`，业务包不使用 `debug`。
- 启动失败时抛 `IllegalStateException`。

**验收**

- 生产环境缺少 JWT 密钥时应用启动失败。
- 生产环境 CORS 配置为 `*` 时应用启动失败。
- 生产环境 Swagger 开启时应用启动失败。

### 3.4 权限与越权治理

**用户端**

所有用户资源必须校验归属：

- 订单详情
- 取消订单
- 退款申请
- 地址修改/删除
- 收藏/足迹
- 评价修改/删除

**商家端**

当前可先保持单商户模型。后续扩展多门店/多商户时，需要引入：

- `shop_id`
- `staff_id`
- `role`
- `permission`
- 数据范围过滤

管理员、店长、店员、客服、财务建议权限拆分：

- 商品管理
- 订单处理
- 退款审核
- 客服聊天
- 报表导出
- 员工管理
- 系统设置

**验收**

- 用户 A 请求用户 B 的订单详情返回 403。
- 普通店员不能访问员工管理接口。
- 客服账号不能导出财务报表。

## 4. P1：上线前强烈建议完成

### 4.1 部署与基础设施加固

**Docker 模式**

- 后端容器必须非 root 用户运行。
- 配置内存和 CPU 限制。
- 日志输出到标准输出或挂载日志目录。
- 健康检查使用 `/actuator/health` 或轻量健康接口。

**systemd 模式**

- 不使用 `User=root`。
- 新建专用用户 `xianguoji`。
- 上传目录、日志目录只授予必要权限。

**网络**

- 公网只开放 `80/443`。
- `8080` 只允许 Nginx 本机访问。
- MySQL `3306` 不对公网开放。
- Redis `6379` 不对公网开放。

**Nginx**

- 强制 HTTPS。
- 配置 `client_max_body_size 10m`。
- 增加慢连接超时限制。
- 反代时正确传递 `X-Real-IP`、`X-Forwarded-For`、`X-Forwarded-Proto`。

**验收**

- 公网无法直接访问 `8080/3306/6379`。
- 后端进程不是 root 用户。
- HTTP 自动跳转 HTTPS。
- 上传超过 10MB 的请求在 Nginx 或后端被拒绝。

### 4.2 CI/CD 与质量门禁

**建议流水线**

- 后端：
  - `mvn test`
  - `mvn package`
  - OWASP Dependency-Check
  - Docker 镜像构建
  - 镜像漏洞扫描
- 商家端：
  - `npm run test`
  - `npm run build`
- 用户端：
  - `npm run test`
  - H5 或小程序构建命令
- 安全：
  - 依赖漏洞扫描
  - 基础 SAST
  - 安全测试脚本 `scripts/security-pentest.sh`
- 发布：
  - 推送镜像
  - 部署预发
  - 自动冒烟
  - 手动确认生产发布
  - 保留最近 3 个可回滚版本

**质量门禁**

- P0/P1 接口测试 100% 通过。
- 后端核心模块覆盖率重点覆盖 `order`、`auth`、`promo`、`catalog`、`cart`。
- 不能存在高危依赖漏洞。
- 构建产物必须来自 CI，不允许手工上传未知 jar。

### 4.3 监控、日志与告警

**业务监控**

- 今日订单数。
- 今日 GMV，模拟支付阶段可统计 `mock_paid_amount`。
- 支付成功率，模拟阶段统计模拟支付接口成功率。
- 退款申请数。
- 退款完成数。
- 下单失败率。
- 库存扣减失败率。
- 拼团成团率。

**系统监控**

- JVM CPU / 内存 / GC。
- Tomcat 线程池。
- 接口 QPS。
- 接口 P95 / P99。
- 5xx 错误率。
- MySQL 连接池。
- Redis 连接池和慢命令。

**安全监控**

- 401 / 403 激增。
- SQL 注入命中。
- XSS 命中。
- 限流命中。
- IP 封禁。
- JWT 黑名单命中。

**日志要求**

- 所有请求带 `traceId`。
- 订单、支付、退款、库存扣减必须打业务日志。
- 手机号、地址、token、验证码必须脱敏。
- 安全日志单独输出到 `security.log`。
- 慢接口单独输出到 `slow.log`。

**告警建议**

- 5 分钟内 5xx 错误率 > 1%。
- 订单提交失败率 > 5%。
- 模拟支付失败率 > 3%。
- Redis 不可用。
- MySQL 连接池耗尽。
- 单 IP 触发安全规则超过阈值。

## 5. P2：生产质量与长期治理

### 5.1 测试补充清单

**必须补的后端测试**

- 模拟支付幂等测试。
- 模拟退款幂等测试。
- 订单状态机非法流转测试。
- 库存扣减并发测试。
- 取消未支付订单与模拟支付并发竞争测试。
- 用户越权访问订单测试。
- 上传伪装文件测试。
- CORS 生产白名单测试。
- JWT 黑名单测试。
- 登录失败锁定测试。

**必须补的前端测试**

- 下单按钮防重复点击。
- 支付按钮防重复点击。
- 退款申请重复提交防护。
- token 过期自动刷新。
- 401/403 统一跳转登录或提示。
- 生产环境 `BASE_URL` 使用 HTTPS。
- WebSocket 断线重连与 token 失效处理。

**必须补的安全测试**

- SQL 注入基础 payload。
- XSS payload。
- 越权访问。
- 大文件上传。
- 伪装图片上传。
- 限流触发。
- CORS 非法 Origin。

### 5.2 数据备份、恢复与审计

**备份策略**

- MySQL 每日全量备份。
- binlog 增量备份。
- 备份保留不少于 14 天。
- 备份文件上传异地 OSS / S3。
- 备份文件开启加密和版本保护。

**恢复演练**

至少每月演练一次恢复到临时库，验证核心表：

- 用户
- 商品
- SKU
- 订单
- 订单明细
- 退款
- 优惠券
- 拼团

**审计日志**

商家端关键操作必须记录：

- 商品上下架
- 改价
- 改库存
- 接单/拒单
- 发货
- 退款审核
- 员工权限变更
- 系统配置变更

**验收**

- 能从备份恢复出最近一天数据。
- 商家端关键操作可以追溯到操作人、时间、IP、变更前后内容。

### 5.3 前端生产化注意事项

**用户端**

- 小程序请求域名必须配置为 HTTPS 合法域名。
- 隐私政策弹窗必须在获取用户信息前展示。
- token 不应明文长期保存，至少做轻量加密或缩短有效期。
- 下单、支付、退款按钮必须做 loading 和禁用。
- 页面不能依赖 mock 数据。

**商家端**

- 生产 `VITE_API_BASE` 必须为 HTTPS。
- 生产 `VITE_WS_URL` 必须为 WSS。
- WebSocket 不建议长期通过 URL 参数传 token，后续可改为短期连接票据。
- 管理后台路由必须做权限校验。
- 导出报表等敏感操作需要二次确认。

**验收**

- 生产构建中搜不到 `127.0.0.1:8080`。
- 生产构建中 `VITE_USE_MOCK` 为 `false`。
- 未登录访问商家后台任意页面都会跳转登录。

## 7. 建议执行顺序

1. **先做 P0**：模拟支付/退款状态机、上传安全、生产配置校验、越权治理。
2. **再做 P1**：部署加固、CI/CD、监控日志告警。
3. **最后做 P2**：测试补齐、备份恢复、审计、前端生产化。
4. **竞争力功能后置**：AI 推荐、订阅水果盒、鲜度溯源等可以等基础质量稳定后再做。
